# 5.0.15 更新说明

> 写给付费客户的人话版。没在真实环境验证过的地方，下面都写明了。
> **本版目前只发布 Linux；Windows / macOS 暂未随本版发布。**

## 修复：卖家号「安全接管」在第二步必崩
- 现象：`tg_takeover_account` 在发起自有登录（T2）时固定报 `unable to open database file`，接管无法完成。
- 原因：新会话文件所在的目录没有先建好，Linux 上打开会话数据库就失败。现已修复；失败时错误信息也会说明是目录问题还是别的，不再只剩一个异常类名。
- 接管失败仍然是干净中止：卖家密钥不会被动，不会注销其他设备，不会改两步验证。

## 修复：云端虚拟机里账号连不上（「隧道可建立，但握手超时」）
- 现象：在云端 Linux 虚拟机里，软件自己的两条连接路线都失败，而同一台机器上别的程序直连 Telegram 一切正常。
- 原因（我们能确定的部分）：以前判断「网络通不通」只看两件事——TCP 443 连得上、代理的 CONNECT 返回 200。但云端虚拟机的出口网关或平台代理常常对任何目标都接受连接，却**不转发 Telegram 的数据**，软件就把一条走不通的线路当成了可用线路。
- 现在：选择线路时会真的发一个 Telegram 起手包并等回应，**只有 Telegram 真的回应了才算通**。直连不通就会去找真正能用的代理；哪条都不通就如实报告，不再假装可用。自检信息也会明确区分「连不上」和「连上了但 Telegram 没有回应」。
- 连接失败时，日志和返回里会带上 Telethon 每次尝试失败的原文，方便定位。

## 注意（如实）
- 以上**没有在真实的 Muse 虚拟机里验证过**，只做了模拟测试（本机回环上的假 Telegram / 假代理）。尤其是「专属代理路线快速失败 5 次」那一条，我们在本机用同样的代理能连通，**没能复现，也没能确认根因**；这一版加了诊断信息，如果仍然失败，请把日志里「最近的连接尝试」那一段发给我们。
- 如果你的虚拟机设置了 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量：软件现在不会再因为它「能 CONNECT」就选它，但如果平台只允许经这个代理出网，软件会如实告诉你哪条路通、哪条不通。
